1. APPROVED DECISIONS AND REMAINING CHOICES
==========================================

D01 — APPROVED: Stabilize expenses first; add income afterward.
The expense release covers Phases 0–7. Income is the first feature in Phase 8.
Do not expand the current release into account balances, income, or own-account
transfers. Preserve compatibility with a later income migration.

D02 — APPROVED: Personal use and explicitly invited friends.
Keep owner pairing, invitations, revocation, and per-user isolation.
Public registration and a commercial multi-tenant service are outside this release.

D03 — APPROVED: Zero OCR budget; free tools plus custom processing/parsing.
Essential slip information:
  1) Where the money went: recipient/payee.
  2) When: transaction date and time.
  3) How much: transferred/actually paid amount.
Start with the existing locally executed Tesseract pipeline. Improve preprocessing,
layout recognition, extraction, and validation before replacing it.
Do not introduce paid OCR, model APIs, transaction verification, or hosting.
A free external API is not automatically authorized to receive private images.
If local options prove insufficient, explain external data handling and quotas
and obtain the user's choice before uploading images. No external OCR is required.

D04 — APPROVED CONSTRAINT: No payments to Supabase or Vercel.
The user accepts a storage design that satisfies this constraint. A particular
retention period has not been approved.
Inspect actual plans, billing behavior, usage, and current official limits before
choosing capacity or retention thresholds. Date the evidence.
Store compact transaction text, not slip images. Bound logs and retries.
Prefer restricting new work or offering export/cleanup over enabling paid capacity.
Do not silently delete account history as quota approaches.
Do not promise unlimited free storage or buy capacity to reach a speed target.
Include LINE message quotas and other dependencies in the zero-cost design.

D05 — APPROVED: No user-facing recovery of deleted expenses.
Single-record deletion and clear-history both require explicit confirmation.
Remove recovery menus, commands, and promises during implementation.
This decision does not authorize deleting existing production records now.
Legacy soft-deleted data needs a scoped transition/purge plan before changing it.
Queue retries, crash recovery, and release rollback remain necessary: these are
different from restoring an expense the user deliberately deleted.

D06 — APPROVED: Use the transfer amount; do not automatically add fees.
Example: transfer 100 THB plus fee 2 THB -> primary expense amount is 100 THB.
Do not require reading or asking about a fee before an expense can be confirmed.
Do not rewrite historical amounts or drop fee columns merely to simplify the UI.
For Paotang subsidy slips, preserve the existing net-out-of-pocket rule:
goods 55 THB minus subsidy 33 THB -> expense 22 THB, not 55 or 88 THB.

D07 — OPTIONAL WORDING CHOICE:
Recommended overview label: "ดูรายจ่าย" (View expenses).
Keep "ดูรายรับรายจ่าย" and current text aliases working.
Ask for a wording preference during screen review if useful. This is not a reason
to block backend work or an invitation to implement income prematurely.

Derived requirements from the approved three-field scope:
- Description, note, category, reference, subsidy, and fee are optional input.
- Preserve useful optional data already available; do not ask mandatory extra questions.
- Default category to "อื่น ๆ" (Other) when no optional category is available.
- A slip with all essential fields proceeds directly to review and confirmation.
- Ask only for essential fields that are missing, invalid, or contradictory.
- Manual expenses may have no transfer recipient: allow explicit unspecified payee.
- User confirmation is still required before any expense contributes to totals.

Ask only when a meaningful unresolved choice is reached:
- Exact history retention after measuring free-tier capacity.
- Sending private images to a free external service, if proposed.
- A material change to product scope or financial meaning.
Do not re-ask D01–D06. Record and implement routine technical choices within scope.

3. KNOWN ISSUES AND EVIDENCE CLASSIFICATION
==========================================

E01 — Confirmed production incident, fixed at the planning baseline:
Overview/summary Flex cards failed with LINE HTTP 400. Decorative boxes lacked
required contents. a9b4444 removed them and added a structural regression check.
Corrected payloads passed LINE validation; deployment smoke passed; affected jobs
were regenerated and completed. Preserve this fix and broaden card coverage.

E02 — User observations, not an instrumented benchmark:
Simple responses/image acknowledgements took about 4–5 seconds. Slip details took
14.69 seconds in one observation and roughly 15–20 seconds in others.
Measure stages before blaming OCR, hosting, or the database.

E03 — User-observed OCR problems:
MAKE: missing date/time; an example read 99.00 as 9.00.
Bangkok Bank: amount missing on some slips.
SCB: date/time and mixed Thai/English recipient names unreliable.
Some recipients were numeric IDs instead of destination names.
Paotang is the user's best-performing provider; protect it against regression.

The following are code-review findings to reproduce, not claims that every
scenario has already occurred in production:

E04: Batch actions reuse one event ID for multiple draft RPC calls, but mutation
     replay is keyed by event_id. One member's result may be replayed for another.
E05: pending() fetches at most 20 rows; the carousel shows at most 10.
     Counts, selections, pagination, and "all" actions need explicit semantics.
E06: Inline text/postbacks and queued images do not share an obvious ordering path.
     Test image -> immediate answer and concurrent deliveries.
E07: Image acknowledgement happens before durable queue insertion.
E08: Rate rejection can produce silence; warning delivery is not awaited.
E09: Retry reuses saved response JSON; a renderer deploy cannot fix that JSON itself.
E10: Recovery restores deleted rows as drafts; single confirmed deletion is hard
     delete. Retire recovery under D05 rather than expanding it.
E11: CSV uses one query; completeness beyond the actual DB row limit is unproven.
E12: Four main OCR fixtures can be skipped when absent. Recipient tests check only
     presence. Some integration assertions still refer to older response wording.
E13: Fixed relative crops and date/time inference from reference IDs need validation.
E14: README claims about queued events differ from the inline implementation.
E15: TypeScript missingField/getMissingFields AND SQL jod_change_draft require a
     description. Changing only the review card will not implement the new scope.
E16: Authorization/rate limiting precedes durable event deduplication. Redelivery
     may consume allowance or repeat notices; reproduce this behavior.

Assign each reproduced issue an acceptance case and owner phase.
Record findings that do not reproduce instead of silently erasing them.


4. TARGET JOURNEYS AND CROSS-COMPONENT CONTRACTS
===============================================

4.1 Primary journeys

Complete slip:
  receive -> durably accept -> acknowledge -> OCR -> review three fields
  -> user confirms -> save once -> success -> report includes expense once.

Incomplete slip:
  receive -> OCR -> ask for missing essential field -> validate answer
  -> ask remaining essentials only -> review -> confirm.

Manual expense:
  start/shortcut -> amount -> date/time (default now, editable)
  -> optional payee or explicitly unspecified -> review -> confirm.
  Preserve shorthand such as "เพิ่มรายการ 45 ค่าอาหาร"; the trailing text can
  populate optional description/category without becoming mandatory.

Manage records:
  select exact record -> edit with version checks -> confirm replacement;
  or select delete -> show exact scope -> explicit confirmation -> remove from totals.

Reports:
  overview/today/month -> confirmed ledger -> category breakdown/recent records
  -> CSV with the same financial meaning.

4.2 Domain invariants

Money:
- Store integer satang; reject nonpositive, malformed, or unsafe-size amounts.
- Never aggregate using floating-point baht arithmetic.
- Distinguish amount from fee, subsidy, gross amount, balance, account, reference.
- Review, database, reports, and CSV all follow D06.

Time:
- Persist a valid instant; display/interpret supported user input in Asia/Bangkok.
- Convert Buddhist years explicitly and reject invalid dates/times.
- Use report intervals [from, until), with boundaries computed in Bangkok time.
- A transaction reference is not automatically a valid date/time source.

Required fields:
- Image expense: positive amount, valid transaction timestamp, recipient.
- Unreadable recipient: ask the user; do not substitute a numeric ID.
- Manual expense: amount/time; allow explicit unspecified recipient.
- Description/category selection must not become hidden prerequisites.
- UI, TypeScript validation, and SQL confirmation must agree.
- Old drafts waiting on optional description/category must have a migration or
  transition path; stale edit_field values must not permanently block confirmation.

Confirmation:
- Drafts are excluded from totals. Confirm explicitly with ownership/version checks.
- Replayed confirmation does not produce another expense or another total.
- Replay lookup must validate the acting user and operation identity before returning
  a saved result; a guessed replay key must not expose another user's data.

Delivery:
- Business completion and outbound delivery are different states.
- Persist results needed for recovery before sending.
- A delivery retry must not rerun a completed mutation.
- Do not promise exactly-once visible LINE delivery under every network condition:
  a timeout may occur after the remote service accepted the message.
- Handle and record unknown acceptance rather than blindly producing another send.

Deletion:
- Confirm exact scope; enforce ownership/version; remove the expense from totals.
- A queued job must not recreate data after clear-history.
- No user-facing restore command or seven-day recovery promise in the target release.
- Minimal replay/audit metadata may remain for a bounded correctness horizon;
  do not retain full deleted private content indefinitely.

4.3 Component responsibilities

LINE adapter -> durable event/order -> command services -> domain/database
                                           |                   |
                                           v                   v
                                     OCR extraction       report query
                                           |                   |
                                           +--> presentation <-+
                                                      |
                                               outbound delivery

Extract responsibilities from lib/bot.ts incrementally where needed.
This diagram does not require a new framework or one table per component.

Settle these logical contracts in Phase 0/1:
- Receipt: user, event ID, sequence, kind, acceptance time, processing state.
- Business result: operation ID, result code, target/version, safe display data.
- Delivery: operation, slot (ack/result/fallback), renderer version, stable retry
  identity, acceptance state, attempts, and error class.
- OCR result: provider/layout, field values, evidence sources, unknown/conflict reasons.
Reuse existing tables where practical. Every new field needs a concrete purpose.

7. PHASE 1 — RELIABLE PROCESSING AND RESPONSES
=============================================
Entry: Phase 0 matrix and event/delivery decisions.
Files: webhook route, lib/jobs.ts, lib/line.ts, lib/access.ts, worker route,
queue/access migrations, tests, scripts/validate-line.ts.
Output: Durable, replay-safe processing with intentional responses.

[x] P1.1 Unify durable acceptance and ordering.
    Deduplicate by event ID before repeating business effects.
    Persist image acceptance before claiming it has been accepted.
    Apply a common per-user policy to queued images and inline mutations.
    An immediate answer after an image must not bind to an unrelated older draft.
    Allow read-only fast paths only when their data semantics remain correct.
    Record deterministic event ordering rather than relying on HTTP scheduling.

[x] P1.2 Separate acceptance, business completion, and delivery.
    Reuse/extend jod_events and jod_mutations with additive migrations as needed.
    Persist recoverable business results before outbound delivery.
    If ack/result use separate delivery slots, their stable retry keys must differ.
    Completion must match the active lease token; stale workers cannot finalize
    or overwrite a newer worker's result.

[x] P1.3 Implement structured error classification.
    Check exact LINE behavior against official documentation during implementation.
    Invalid Flex payload -> plain-text fallback from the same saved business result.
    Invalid/expired reply token -> designed push fallback, no repeated mutation.
    Auth/config failure -> actionable failure, not repeated blind retries.
    Rate/quota failure -> distinguish throttling from depleted allowance.
    Timeout -> potentially unknown acceptance, not proof the message was rejected.
    DB transient error -> retry the correct stage, preserving completed effects.
    Mark done only after the defined delivery success/acceptance condition.

[x] P1.4 Repair persisted invalid responses safely.
    Store renderer version and sufficient safe result data when necessary.
    Repair tooling previews criteria/count and selects known affected jobs.
    Regenerate delivery content without re-confirming/re-editing/re-deleting.
    Preserve retry identity after uncertain acceptance.
    For definitively rejected content, follow documented retry-key rules and
    record any replacement attempt; do not assume arbitrary key reuse is safe.
    Never clear the entire queue to repair one card.

[x] P1.5 Make rate limiting visible and replay-aware.
    Recommended: duplicate delivery of one logical event consumes allowance once.
    Send a brief bounded Thai notice when the user is limited and transport permits.
    Throttle notices themselves and await/schedule delivery reliably.
    Test boundary counts, duplicate events, and the next time window.

[x] P1.6 Add privacy-conscious timing.
    Measure received, authorized, durable accepted, queued, claimed, downloaded,
    processed, rendered, LINE accepted, and retry durations.
    Log IDs/stages/error classes, not secrets, images, or full OCR text.
    Bound retention. Do not duplicate whole private results in metrics.
    Keep server-to-LINE and user-visible latency as separate measurements.

[x] P1.7 Expand LINE validation coverage.
    Validate overview, today/month, review, edit, pending, delete/clear, export,
    menus, quick replies, and postbacks.
    Include empty states, long Thai/English text, max supported items/categories.
    Batch within current documented API limits.
    Use validation endpoints; do not send fixtures to real users.

[x] P1.8 Test crash, lease, and concurrency behavior.
    Crash before commit, after commit/before send, and after possible remote acceptance.
    Expired lease can be reclaimed; stale lease cannot finalize current work.
    One user's slow OCR must not globally lock unrelated users.
    Permanent failures must not spin forever or starve later work.
